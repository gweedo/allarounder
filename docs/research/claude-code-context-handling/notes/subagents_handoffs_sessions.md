# Subagents, handoff files, and session-per-task workflows for clean Claude Code context (as of Oct 2026)

Source-type legend: **[OFFICIAL-DOCS]** = code.claude.com docs (live as of 2026-10-18; version numbers like v2.1.2xx quoted from them). **[ANTHROPIC-ENG]** = anthropic.com/engineering or Claude Code team blog (dated; may describe older models). **[PRACTITIONER]** = Matt Pocock / aihero / community; opinion, not official. **[LOCAL]** = skills installed in this repo at `.claude/skills/`.

## Q1. Subagents (Agent tool, custom .claude/agents, Explore/Plan, forks): when they save main-context tokens vs waste them, and what to delegate

### Takeaway
Subagents save *main-context* tokens (the verbose work stays in their window; only a summary returns) but always cost *more total* tokens, and a non-fork subagent starts cold and must re-derive context. Delegate self-contained, read-heavy, verbose work (broad searches, research, log/test processing, independent review); keep iterative, tightly coupled, latency-sensitive, or quick targeted work in the main thread. Forks (new in 2026) close much of the cold-start gap: they inherit the full conversation and reuse the parent's prompt cache.

### Cited Findings
**What a subagent is / what it sees (official)**
- "Use one when a side task would flood your main conversation with search results, logs, or file contents you won't reference again: the subagent does that work in its own context and returns only the summary." [OFFICIAL-DOCS] — [Subagents](https://code.claude.com/docs/en/sub-agents)
- A non-fork subagent "starts with a fresh, isolated context window. It doesn't see your conversation history, the skills you've already invoked, or the files Claude has already read. Claude composes a delegation message that summarizes the task." Its initial context is: its system prompt, the task message, CLAUDE.md files, git status snapshot, preloaded skills, and a sibling roster; output style and auto memory do not reach it. [OFFICIAL-DOCS] — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Built-ins: **Explore** (read-only, fast codebase search), **Plan** (read-only research in plan mode), **general-purpose** (all tools), plus statusline-setup (Sonnet) and claude-code-guide (Haiku). Explore and Plan *skip CLAUDE.md and the git status snapshot* "to stay fast and cheap"; you can run Explore on a cheaper model by defining a project/user agent named `Explore` with `model: haiku`. Explore and Plan are one-shot and cannot be resumed. [OFFICIAL-DOCS] — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Custom subagents are Markdown + YAML frontmatter in `.claude/agents/` (project) or `~/.claude/agents/` (user); only `name` and `description` are required; `tools`, `model`, `isolation: worktree`, hooks, `autoCompactWindow` are optional. A startup warning fires if combined custom-agent descriptions exceed 15,000 tokens. [OFFICIAL-DOCS] — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Resumable: "Resumed subagents retain their full conversation history, including all previous tool calls, results, and reasoning" (via `SendMessage` with the agent ID/name). Transcripts live at `~/.claude/projects/{project}/{sessionId}/subagents/agent-{agentId}.jsonl`, deleted after `cleanupPeriodDays` (default 30). Defaults: max 20 concurrent subagents, nesting depth 3. [OFFICIAL-DOCS] — [Subagents](https://code.claude.com/docs/en/sub-agents)

**Forks (2026 feature)**
- "A fork is a subagent that inherits the entire conversation so far instead of starting fresh… The fork's own tool calls still stay out of your conversation and only its final result comes back." Started with `/subtask …` (v2.1.212+; earlier `/fork`). Fork mode is on by default in interactive sessions (v2.1.232+), off in `-p`/Agent SDK; `CLAUDE_CODE_FORK_SUBAGENT=0|1` overrides. A fork can't spawn further forks; it can take `isolation: "worktree"`. [OFFICIAL-DOCS] — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Fork vs non-fork table: fork = full history, same system prompt/tools/model, **prompt cache shared with main session**; non-fork = fresh context, own definition/model, **separate cache**. "Because of that reuse, a fork costs less than a fresh subagent for tasks that need the same context." [OFFICIAL-DOCS] — [Subagents](https://code.claude.com/docs/en/sub-agents)

**When to use vs not (official decision rule)**
- Use the main conversation when: the task needs frequent back-and-forth; "multiple phases share significant context"; it's a quick targeted change; "Latency matters. A subagent that isn't a fork starts fresh and may need time to gather context." Use subagents when: output is verbose and not needed in main context; you want tool restrictions; the work is self-contained and can return a summary. [OFFICIAL-DOCS] — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Cost caveats: "Each subagent spends tokens of its own while it runs"; "Running many subagents that each return detailed results can consume significant context." [OFFICIAL-DOCS] — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Best practices: "Delegate research with 'use subagents to investigate X'. They explore in a separate context, keeping your main conversation clean for implementation." The "infinite exploration" failure pattern (unscoped "investigate" reads hundreds of files) is fixed by scoping narrowly or using subagents. [OFFICIAL-DOCS] — [Best practices](https://code.claude.com/docs/en/best-practices)
- Adversarial review: "Before treating a task as done, have a subagent review the diff in a fresh context and report gaps." A reviewer "sees only the diff and the criteria you give it, not the reasoning that produced the change." Caveat: a reviewer told to find gaps "will usually report some, even when the work is sound… Chasing every finding leads to over-engineering"; tell it to flag only correctness/requirement gaps. [OFFICIAL-DOCS] — [Best practices](https://code.claude.com/docs/en/best-practices)
- Cost docs: "Delegate verbose operations to subagents" (running tests, fetching docs, processing logs); pick a smaller model (`model: haiku`) for simple subagent tasks; subagent requests still draw on your usage and appear in `/usage` attribution. [OFFICIAL-DOCS] — [Manage costs](https://code.claude.com/docs/en/costs)
- Agent teams (experimental, off by default; `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`) "use approximately 7x more tokens than standard sessions when teammates run in plan mode"; token usage "roughly proportional to team size." [OFFICIAL-DOCS] — [Manage costs](https://code.claude.com/docs/en/costs)

**Token-cost multipliers from Anthropic's multi-agent research post (June 13, 2025 — Claude Opus 4/Sonnet 4 era; research product, not Claude Code; treat numbers as dated)**
- "agents typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens than chats." [ANTHROPIC-ENG] — [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Multi-agent (Opus 4 lead + Sonnet 4 subagents) beat single-agent Opus 4 by 90.2% on their internal research eval; token usage alone explained ~80% of BrowseComp performance variance (95% with tool calls + model choice). [ANTHROPIC-ENG] — [Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Poor fits: "domains that require all agents to share the same context or involve many dependencies between agents"; "most coding tasks involve fewer truly parallelizable tasks than research"; agents are not yet good at real-time coordination/delegation. [ANTHROPIC-ENG] — [Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Subagents act as filters/compressors returning condensed findings; filesystem pattern: subagents "store their work in external systems, then pass lightweight references back to the coordinator." Near limits, agents "spawn fresh subagents with clean contexts while maintaining continuity through careful handoffs." [ANTHROPIC-ENG] — [Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Context engineering post (Sep 29, 2025): each sub-agent "might explore extensively, using tens of thousands of tokens or more, but returns only a condensed, distilled summary of its work (often 1,000-2,000 tokens)." Choose compaction for back-and-forth flows, structured note-taking for iterative development with milestones, multi-agent for complex research/analysis with parallel exploration. [ANTHROPIC-ENG] — [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

**Cache interaction (relevant to "waste")**
- A non-fork subagent's "first request doesn't read the parent's cache, because the two prefixes differ"; subagents fall in the 5-minute TTL bucket even on a subscription (main conversation gets 1 hour). The parent's cache is unaffected by spawning a subagent. A fork's first request reads the parent's cache. [OFFICIAL-DOCS] — [Prompt caching](https://code.claude.com/docs/en/prompt-caching)
- Claude Code team: don't switch models mid-session to save money (per-model caches); instead use subagents for model switches — "Opus writes a hand-off message, and Explore subagents run on Haiku." (Apr 30, 2026) [ANTHROPIC-ENG] — [Prompt caching is everything](https://claude.dev/blog/lessons-from-building-claude-code-prompt-caching-is-everything/)

**Local baseline [LOCAL]**
- The repo's `review` skill runs Standards and Spec reviews "in parallel sub-agents"; `ask-matt` uses subagents implicitly via `/review` after `/implement`. `qa` "explores the codebase in the background for context". — local `.claude/skills/review`, `.claude/skills/ask-matt/SKILL.md`

### Inferences
- Rule of thumb for a solo dev: a subagent pays off when (tokens it would dump into main context) >> (cost of writing a self-contained brief + its summary ~1–2k tokens). Broad "where is X / how does Y work across the repo" searches, web research, test/log triage, and fresh-eyes diff review clear that bar; a 3-file targeted edit does not.
- Prefer a **fork** when the side task needs what the main thread already knows (e.g. "draft tests for the parser changes so far") — no re-derivation, cache reuse. Prefer a **fresh** subagent when you specifically want *no* bias from the main thread (adversarial review) or a restricted toolset/cheaper model.
- The 4×/15× multipliers are total-spend warnings, not main-context costs; on a flat subscription they translate into faster limit consumption rather than a bill. They were measured on a research system with 2025 models, so don't over-apply to coding.
- Explore skipping CLAUDE.md means project rules (e.g. this repo's Italian/English rule) won't reach it — fine for search, but don't use Explore for anything that needs project conventions.

### Gaps
- No official quantitative figure for how many main-context tokens a typical Claude Code subagent call saves, or for the "re-derivation overhead" of a cold subagent; only qualitative guidance plus the 1–2k summary figure from the context-engineering post.
- No 2026 Anthropic re-measurement of the 4×/15× multipliers for current models or for Claude Code specifically.

## Q2. Handoff files: what shape works best for passing context to a fresh session

### Takeaway
The best-evidenced pattern (Anthropic's long-running-harness post) is *structured external state + git*: a progress log, a machine-readable feature/task list the agent can only tick, an init script, and descriptive commits — plus a fixed "get your bearings" routine at session start. Matt Pocock's `/handoff` is a minimal, reference-don't-duplicate variant. Community templates converge on: completed, pending, decisions + why, pitfalls/dead ends, files, next steps — with a growing emphasis on verifying claims against git before trusting them.

### Cited Findings
**Anthropic "Effective harnesses for long-running agents" (Nov 26, 2025) [ANTHROPIC-ENG]** — [source](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Problem: each new session starts with no memory; "compaction isn't sufficient" — it "doesn't always pass perfectly clear instructions to the next agent."
- Two prompts, same harness: an **initializer agent** (first session) creates `init.sh`, `claude-progress.txt`, and an initial git commit; a **coding agent** (every later session) makes incremental progress on *one feature* and leaves structured updates.
- **Feature list in JSON** (200+ features for a claude.ai clone), all starting `passes: false`, each with `category`, `description`, `steps`. Agents may only flip `passes`: "It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality." JSON chosen because the model is less likely to inappropriately overwrite it than Markdown.
- **Progress file** + git history let a fresh context understand state quickly; agents write a summary at session end. **Git**: descriptive commits, revert bad changes, end each session in a "clean state" mergeable to main.
- **Session-start routine**: `pwd` → read git log + progress file → read feature list, pick highest-priority failing feature → run `init.sh` → run a basic end-to-end check before new work (catches bugs left by the previous session; saves tokens re-learning how to run the app).
- Failure modes fixed: one-shotting and running out of context mid-feature (→ one feature at a time); premature "done" (→ feature list + self-verification, E2E/browser testing rather than unit/curl only).

**Matt Pocock `/handoff` [LOCAL / PRACTITIONER]** — local `.claude/skills/handoff/SKILL.md`
- "Compact the current conversation into a handoff document for another agent to pick up." Save to the OS temp directory, *not* the workspace. Include a "suggested skills" section. "Do not duplicate content already captured in other artifacts (PRDs, plans, ADRs, issues, commits, diffs). Reference them by path or URL instead." Redact secrets/PII. Optional argument = what the next session is for; tailor the doc to it. `disable-model-invocation: true` (user-triggered only).
- `ask-matt` positions it: "`/handoff` forks; `/compact` continues." Use `/handoff` when you want a fresh session but need the conversation preserved, or to branch into a `/prototype` session and back; use `/compact` only "at intentional breaks between phases… Don't compact mid-phase — the agent can lose its way." — local `.claude/skills/ask-matt/SKILL.md`
- Third-party summaries describe it as capturing WIP state, decisions and blockers, and report Pocock calls it his most-used skill — [vibeindex](https://vibeindex.ai/skills/mattpocock/skills/handoff); [m.163.com (Chinese tutorial)](https://m.163.com/dy/article/L39VQQFN05566SCS.html) (secondary; not verified against a primary Pocock source).

**Official docs**
- Interview → spec → fresh session: "Keep interviewing until we've covered everything, then write a complete spec to SPEC.md. Once the spec is complete, start a fresh session to execute it." "The most useful specs are self-contained: they name the files and interfaces involved, state what is out of scope, and end with an end-to-end verification step." [OFFICIAL-DOCS] — [Best practices](https://code.claude.com/docs/en/best-practices)
- If continuing via compaction instead, steer it: CLAUDE.md line like "When compacting, always preserve the full list of modified files and any test commands"; `/compact <focus>`; `/rewind` → "Summarize from here / up to here" for partial compaction. [OFFICIAL-DOCS] — [Best practices](https://code.claude.com/docs/en/best-practices)
- Context-engineering post: structured note-taking (to-do lists, `NOTES.md`) outside the window is a primary long-horizon technique alongside compaction. [ANTHROPIC-ENG] — [Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

**No built-in handoff file**
- GitHub issue #11455 proposes a standardized `.claude/handoff.md` (sections: Completed This Session / Pending / Context Notes incl. decisions, blockers, reference files / Next Steps) with SessionEnd/SessionStart hooks; still **open, no Anthropic response**, latest comment Oct 11, 2026. Community points: handoffs can record unverified "done" claims (verify against commits/git), may never be written if a session crashes or hits a usage limit (write incrementally), and parallel sessions need per-session scoping. — [anthropics/claude-code#11455](https://github.com/anthropics/claude-code/issues/11455)
- Community skills converge on similar sections (completed, open, key decisions, known pitfalls, next steps), some validating paths on disk, scanning for secrets and checking staleness vs git history — e.g. [392fyc/claude-handoff](https://github.com/392fyc/claude-handoff), [skills.sh handoff variants](https://skills.sh/steveclarke/dotfiles/handoff) [PRACTITIONER; quality unvetted].

### Inferences
- Synthesized recommended shape (combining the above): **Goal / what the next session is for** → **Current state** (branch, last commit, what passes/fails, verified by command output) → **Decisions + why** (link ADR/issue rather than restate) → **Files touched** → **Dead ends / what NOT to redo** → **Open questions** → **Next steps (ordered, first one concrete)** → **How to verify / run** (or point at init script/CLAUDE.md commands) → **Suggested skills**. Keep it short by referencing durable artifacts.
- The Anthropic harness separates *stable spec* (JSON feature list, edit-restricted) from *running log* (progress file). For this repo, the GitHub issue/PRD plays the spec role and the handoff/PR description plays the log role.
- Pocock's "save to temp dir, not workspace" deliberately makes handoffs disposable; anything that must outlive the session belongs in an issue, ADR, or commit instead.

## Q3. One fresh session per issue/task; issues/PRDs as durable context carrier; plan files; worktrees for parallel sessions

### Takeaway
Official guidance and Pocock agree: clear (or start fresh) between unrelated tasks, keep one coherent phase per window, and carry context across windows in durable artifacts (spec/PRD/issue/plan file/git), not in chat history. Worktrees (`claude --worktree`) are the official mechanism for parallel sessions; writer/reviewer split across sessions is an officially recommended quality pattern.

### Cited Findings
- "Most best practices are based on one constraint: Claude's context window fills up fast, and performance degrades as it fills." [OFFICIAL-DOCS] — [Best practices](https://code.claude.com/docs/en/best-practices)
- "Use `/clear` frequently between tasks"; "kitchen sink session" failure → `/clear` between unrelated tasks. "If you've corrected Claude more than twice on the same issue in one session… Run `/clear` and start fresh… A clean session with a better prompt almost always outperforms a long session with accumulated corrections." Counterpoint: "Sometimes you *should* let context accumulate because you're deep in one complex problem and the history is valuable." [OFFICIAL-DOCS] — [Best practices](https://code.claude.com/docs/en/best-practices)
- Sessions: name with `/rename` "and treat them like branches: each workstream gets its own persistent context"; `claude --continue` / `--resume`. [OFFICIAL-DOCS] — [Best practices](https://code.claude.com/docs/en/best-practices)
- Explore → plan → implement → commit; plan mode with `Ctrl+G` to edit the plan; skip planning "If you could describe the diff in one sentence." [OFFICIAL-DOCS] — [Best practices](https://code.claude.com/docs/en/best-practices)
- Example official skill `/fix-issue` uses `gh issue view` as the context source — the issue is the task carrier. Prefer `gh` CLI as "the most context-efficient way to interact with external services." [OFFICIAL-DOCS] — [Best practices](https://code.claude.com/docs/en/best-practices)
- Writer/Reviewer across two sessions: "A fresh context improves code review since Claude won't be biased toward code it just wrote." [OFFICIAL-DOCS] — [Best practices](https://code.claude.com/docs/en/best-practices)
- Parallel options listed officially: worktrees, cross-session messaging, desktop app sessions, cloud sessions, agent view (`claude agents`, research preview), agent teams (experimental); `/batch` splits a change across 5–30 subagents, each in its own worktree. [OFFICIAL-DOCS] — [Best practices](https://code.claude.com/docs/en/best-practices)
- Worktrees: `claude --worktree <name>` creates `.claude/worktrees/<name>/` on branch `worktree-<name>`, branched by default from the remote default branch (`worktree.baseRef: "fresh"`; `"head"` to carry local work); `claude --worktree "#1234"` branches from a PR; `.worktreeinclude` copies gitignored files like `.env`; add `.claude/worktrees/` to `.gitignore`; clean unnamed worktrees auto-removed on exit, dirty ones prompt; `isolation: worktree` in subagent frontmatter; worktree sessions are blocked from editing/running git in the main checkout. Each worktree is a fresh checkout — dependencies must be installed there. [OFFICIAL-DOCS] — [Worktrees](https://code.claude.com/docs/en/worktrees)
- Pocock main flow [LOCAL/PRACTITIONER]: `/grill-with-docs` → `/to-prd` → `/to-issues` in **one unbroken context window** ("don't compact or clear until after `/to-issues`"), then "clear context between each one: start a fresh session per issue and kick off `/implement` by passing it the PRD and the single issue." Single-session builds just `/implement` in place. Issues produced by `/to-issues` are "agent-ready" and should not be re-triaged. — local `.claude/skills/ask-matt/SKILL.md`; `/implement` = TDD at pre-agreed seams, typecheck and single tests regularly, full suite at end, `/review`, commit — local `.claude/skills/implement/SKILL.md`
- "Smart zone" [PRACTITIONER]: Pocock's ask-matt cites ~120k tokens as the window within which the model "still reasons sharply"; aihero's dictionary entry says the "dumb zone" "commonly begins around 125K–150K tokens — though this is debated" and that the zones don't track the advertised window size; secondary sources attribute the term to Dex Horthy (HumanLayer) and cite ~100k or ~40% utilization. Advice: clear/compact, one task per session. — [aihero smart zone](https://www.aihero.dev/ai-coding-dictionary/smart-zone) (via search snippet; direct fetch 404'd), [garrit.xyz](https://garrit.xyz/posts/2026-05-06-dont-trust-large-context-windows), [pi-context-zone README](https://cdn.jsdelivr.net/gh/arpagon/pi-context-zone@main/README.md)
- Anthropic's context-rot framing supports this qualitatively: recall "decreases" as context grows; degradation is gradual, not a cliff. [ANTHROPIC-ENG] — [Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

### Inferences
- For this repo (GitHub Issues + PRDs + ADRs + CLAUDE.md already in place), the issue/PRD *is* the handoff for implementation sessions; a `/handoff` doc is only needed for unfinished mid-task work or for branching into a prototype.
- One-session-per-issue costs little: CLAUDE.md + system prompt are re-sent each new session but are a small, often-cached prefix (see Q4), whereas a long multi-issue session resends all accumulated history every turn.
- Worktrees matter only when actually running sessions *in parallel*; a solo dev doing sequential issues can stay on feature branches in one checkout (this repo's memory already notes worktrees go in `.claude/worktrees`).
- Smart-zone thresholds (100k–150k) are practitioner heuristics without published benchmark backing; the official docs give no token number, only "performance degrades as it fills."

### Gaps
- No controlled study found comparing "fresh session per issue" vs long sessions on outcome quality in Claude Code; evidence is official guidance + practitioner reports.
- No official token threshold for when to clear; status-line context % is the recommended monitoring tool.

## Q4. Prompt-cache considerations: long sessions vs fresh sessions (cost)

### Takeaway
Long sessions are cheap per turn only while cached, but every turn still re-reads the whole history at the cached rate, cache misses after idle (>1h on subscription main thread, 5m on API/subagents) reprocess everything, and compaction is itself a large request. `/clear` "costs nothing"; a fresh session reuses the cached system-prompt/project prefix when started in the same directory with matching git snapshot. Net: for unrelated tasks, fresh sessions are both cheaper and better.

### Cited Findings
- Cache is prefix-matched and exact; layers ordered system prompt+tools → project context (CLAUDE.md, auto memory) → conversation. "A change to the system prompt invalidates everything." [OFFICIAL-DOCS] — [Prompt caching](https://code.claude.com/docs/en/prompt-caching)
- Invalidators: switching models, changing effort (except on Opus/Sonnet/Haiku 5.5 & Fable 5.1 via API key/subscription), turning on fast mode, MCP/plugin tool-set changes (mostly avoided by deferred tool search), denying a whole tool (without tool search), compaction, many images, upgrading Claude Code. Cache-safe: editing repo files, editing CLAUDE.md (but edit doesn't apply until `/clear`/`/compact`/restart), permission mode changes, output style, invoking skills/commands, `/recap`, `/rewind`, spawning subagents. [OFFICIAL-DOCS] — [Prompt caching](https://code.claude.com/docs/en/prompt-caching)
- TTL: main conversation gets **1 hour** on a Claude subscription within plan usage; **5 minutes** on usage credits, API key, or cloud provider; subagents/forks/compaction/workflows get 5 minutes by default. Override via `promptCacheTtl` / `subagentPromptCacheTtl` (v2.1.242+). [OFFICIAL-DOCS] — [Prompt caching](https://code.claude.com/docs/en/prompt-caching)
- "Why usage climbs in a long session": "Claude Code sends your full conversation with every request… a one-line question in a session that has been open all day still draws usage for the whole conversation"; first message after a break longer than the TTL "misses the cache and reprocesses your full context"; "`/compact` reads the conversation it summarizes, so compacting a large context is itself a large request. When you want a fresh start instead of continuity, `/clear` costs nothing." [OFFICIAL-DOCS] — [Manage costs](https://code.claude.com/docs/en/costs)
- Compaction while cache is warm "costs a fraction of what the context size suggests"; after the TTL it "reprocesses the full history as uncached input," which is why `/compact` "costs the most when you resume an old session." `/rewind` truncates to an already-cached prefix, so it's cheaper than compaction for abandoning a path. Run `/compact` at natural breaks rather than letting auto-compaction trigger mid-task. Idle sessions on 1h TTL may auto-compact shortly before expiry (`idleCompaction`, v2.1.290+). [OFFICIAL-DOCS] — [Prompt caching](https://code.claude.com/docs/en/prompt-caching)
- Cache scope: "Sessions you run in parallel in the same directory build matching prefixes and read each other's cache. Sequential sessions share the prefix only when the git status snapshot taken at startup matches." Different directories (e.g. different worktrees) miss each other's cache. [OFFICIAL-DOCS] — [Prompt caching](https://code.claude.com/docs/en/prompt-caching)
- Claude Code team (Apr 30, 2026): cache-safe compaction (reusing the parent prefix and appending the compaction prompt) costs about one-tenth of an uncached call; resulting summary ~20k tokens; "a few percentage points of cache miss rate can dramatically affect cost and latency"; the team alerts on hit rate and declares SEVs when it drops. [ANTHROPIC-ENG] — [Prompt caching is everything](https://claude.dev/blog/lessons-from-building-claude-code-prompt-caching-is-everything/)
- Monitoring: `/usage` "Prompt cache (main)" line shows hit %, misses, likely cause, warm/cold + TTL (v2.1.251+); it covers main conversation only, not subagents. `/clear` resets session totals (v2.1.211+). Enterprise average ~$13/dev/active day, $150–250/month; high API spend "usually traces back to long sessions that were never cleared or to Opus left as the default model." [OFFICIAL-DOCS] — [Manage costs](https://code.claude.com/docs/en/costs)
- Tip: "Pick your model and effort level at the top of a session, then save `/compact` for natural breaks between tasks." [OFFICIAL-DOCS] — [Prompt caching](https://code.claude.com/docs/en/prompt-caching)

### Inferences
- For a subscription user, the cost lever is plan-limit consumption: a long, idle-and-return session pays a full uncached re-read on return; a fresh session pays only a small (often cached) system+CLAUDE.md prefix. Prefer `/clear` (or a new session) over `/compact` when the next task doesn't need continuity.
- Subagents' 5-minute TTL means long-running background subagents with pauses will re-pay their own context; forks avoid the parent cache miss on their first turn but still fall in the 5-minute bucket thereafter.
